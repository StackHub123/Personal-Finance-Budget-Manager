================================================================================
DETAILING OF WORKFLOW

PERSONAL FINANCE & BUDGETING DASHBOARD
Fully Expanded End-to-End Master Project Workflow


PROJECT PROBLEM STATEMENT
--------------------------------------------------------------------------------
Personal Finance & Budgeting Dashboard: A CLI or basic GUI frontend attached to
a persistent SQLite/File backend to track expenses.

Required: Frontend/Backend separation, Transaction and Account classes, file
serialization.



################################################################################
# PHASE 0 -- UNDERSTAND THE PROBLEM
################################################################################


0.1 Read exact problem statement
--------------------------------------------------------------------------------
First, we read the problem statement carefully from beginning to end without
making implementation assumptions. We identify every noun, action, technology,
and restriction mentioned in the statement. We then rewrite the statement in
simple terms so that both team members have the same understanding of what must
be built.

Actions:
    1. Read the complete problem statement.
    2. Highlight every explicitly required component.
    3. Identify what the words "dashboard," "frontend," "backend,"
       "persistent," "SQLite/File," "Transaction," "Account," and
       "serialization" imply.
    4. Separate requirements from optional interpretations.
    5. Write the requirements in our own words.
    6. Review the interpretation with both project members so that both
       members agree on what the project means.

Output:
    A clear, shared understanding of the problem statement.


0.2 Extract mandatory requirements
--------------------------------------------------------------------------------
We now convert the problem statement into an explicit checklist of things that
the final application must contain.

Actions:
    1. Record that the application must have a CLI or basic GUI frontend.
    2. Record that persistent storage is required.
    3. Decide on the persistent backend during the design phase. SQLite is the
       planned primary choice unless the final project requirements or technical
       constraints justify using file-based persistence instead.
    4. Record that the application must track expenses and therefore must have
       a transaction-management mechanism.
    5. Record that frontend and backend responsibilities must be separated.
    6. Record that Account and Transaction must be implemented as OOP classes.
    7. Record that file serialization must be implemented.
    8. Record that the overall implementation must remain consistent with the
       OOP course requirements.
    9. Convert these requirements into a project-completion checklist.

Output:
    A formal list of mandatory project requirements.


0.3 Identify implied expectations
--------------------------------------------------------------------------------
Some requirements are not written as individual feature names but are naturally
required for the system to function properly. We identify these before
designing the project.

Actions:
    1. Determine that accounts need to be created and managed because
       transactions must belong to some account.
    2. Determine that transactions need income/expense information because
       financial analysis requires both incoming and outgoing money.
    3. Determine that categories are required to understand where money is
       being spent.
    4. Determine that budgeting requires budget limits and spending
       comparisons.
    5. Determine that a dashboard needs calculated financial summaries.
    6. Determine that validation is needed so that incorrect user input does
       not corrupt the data.
    7. Determine that persistence requires reading previously stored data when
       the application starts.
    8. Determine that imported transactions need duplicate handling if
       statement import is supported.
    9. Determine that a usable application needs error handling and clear user
       interaction.

Output:
    A list of functional expectations that are implied by the problem
    statement.


0.4 Define what the project is NOT required to do
--------------------------------------------------------------------------------
We explicitly identify functionality that is not necessary for satisfying the
assignment so that the project does not become unnecessarily large.

Actions:
    1. Record that real-time bank synchronization is not required.
    2. Record that the application will not ask users for internet-banking
       passwords.
    3. Record that direct bank API integration is not a core requirement.
    4. Record that mobile-app development is not required.
    5. Record that a large commercial banking website is not required.
    6. Record that cloud deployment is not required.
    7. Record that online payment processing is not required.
    8. Record that advanced AI-based financial advice is not required.
    9. Keep these items available as possible future-scope ideas instead of
       treating them as current development tasks.

Output:
    A clearly defined boundary around the project.

# PHASE 3 -- REQUIREMENTS & USER WORKFLOWS
################################################################################


3.1 Account workflow
--------------------------------------------------------------------------------
We determine exactly what happens when a user creates, views, edits, or deletes
an account.

Actions:
    1. User opens the account-management section.
    2. User chooses to create an account.
    3. Application asks for account details.
    4. Input is validated.
    5. An Account object is created.
    6. Business logic confirms that the account is valid.
    7. The repository stores the account in SQLite.
    8. The application confirms successful creation.
    9. Similar workflows are designed for viewing, updating, and deleting
       accounts.

Output:
    A complete account-management workflow.


3.2 Manual transaction workflow
--------------------------------------------------------------------------------
We define how a user quickly records an expense.

Actions:
    1. User chooses "Add Expense."
    2. Application asks for amount, account, category, description, and date.
    3. Application validates the entered information.
    4. A Transaction object is created.
    5. Business logic processes the transaction.
    6. The repository stores the transaction.
    7. SQLite persists the transaction.
    8. The application displays a confirmation.

Output:
    A complete manual expense-entry workflow.


3.3 Manual income workflow
--------------------------------------------------------------------------------
We define how incoming money is recorded.

Actions:
    1. User chooses "Add Income."
    2. Application requests the required transaction information.
    3. Application validates the information.
    4. A Transaction object is created.
    5. Business logic processes it as income.
    6. The transaction is stored through the repository.
    7. SQLite persists it.
    8. The application confirms the operation.

Output:
    A complete income-entry workflow.


3.4 Statement import workflow
--------------------------------------------------------------------------------
We define how a user can periodically import transactions from a downloaded
bank statement.

Actions:
    1. User downloads a statement from their bank.
    2. User selects the statement file in our application.
    3. Application identifies the supported statement format.
    4. Application reads the file.
    5. The parser extracts transaction information.
    6. The extracted information is converted into structured transaction data.
    7. Transaction data is validated.
    8. Possible duplicates are identified.
    9. The user reviews or confirms the import when required.
    10. Valid new transactions are converted into Transaction objects.
    11. Transactions are sent into the common transaction-processing pipeline.
    12. Valid transactions are saved to SQLite.

Output:
    A statement-import workflow that supplements manual entry.


3.5 Duplicate detection workflow
--------------------------------------------------------------------------------
We prevent the same transaction from being stored twice.

Actions:
    1. Receive an imported transaction.
    2. Search existing stored transactions.
    3. Compare relevant identifying fields such as date, amount, account, and
       description.
    4. Determine whether there is no match, a possible duplicate, or an
       obvious duplicate.
    5. Mark possible duplicates for review.
    6. Allow the application to skip or request confirmation according to the
       final design.
    7. Save only transactions that should actually be inserted.

Output:
    A duplicate-prevention mechanism.


3.6 Category workflow
--------------------------------------------------------------------------------
We determine how transactions are assigned to categories.

Actions:
    1. Receive the transaction description.
    2. Check whether the user has already supplied a category.
    3. For imported transactions, compare the description against known rules.
    4. Assign a matching category when appropriate.
    5. Use a fallback such as Other when no rule matches.
    6. Allow manual correction where necessary.
    7. Store the final category with the transaction.

Output:
    A consistent transaction categorization process.


3.7 Budget workflow
--------------------------------------------------------------------------------
We define how users create and monitor budgets.

Actions:
    1. User opens the budget section.
    2. User selects a category.
    3. User selects a month and year.
    4. User enters a budget limit.
    5. Application validates the budget.
    6. A Budget object is created.
    7. The budget is stored.
    8. Later, transaction data is compared against the budget.
    9. Spending is calculated.
    10. Remaining budget is calculated.
    11. Over-budget conditions are identified.

Output:
    A complete budget-management workflow.


3.8 Dashboard workflow
--------------------------------------------------------------------------------
We define how financial information reaches the dashboard.

Actions:
    1. User opens the dashboard.
    2. Application requests relevant data from the business layer.
    3. Business logic retrieves transactions and budget information.
    4. Income is calculated.
    5. Expenses are calculated.
    6. Savings are calculated.
    7. Category spending is calculated.
    8. Budget usage is calculated.
    9. Over-budget categories are identified.
    10. Results are formatted for display.
    11. Frontend displays the results.

Output:
    A defined dashboard workflow.


3.9 Reports workflow
--------------------------------------------------------------------------------
We define how users request financial reports.

Actions:
    1. User opens the reports section.
    2. User selects a report type.
    3. User selects a time range such as a month.
    4. Business logic retrieves the relevant transactions.
    5. Transactions are filtered.
    6. Data is grouped or summarized as needed.
    7. Totals are calculated.
    8. Results are formatted.
    9. The report is displayed.

Output:
    A defined reporting workflow.


3.10 Backup/restore workflow
--------------------------------------------------------------------------------
We define how data is backed up and restored.

Actions:
    1. User chooses export/backup.
    2. Application retrieves required application data.
    3. Data is converted into a serializable format.
    4. Serializer writes the data to a file.
    5. User receives confirmation that the backup was created.
    6. For restoration, the application reads the backup file.
    7. Serializer converts the file representation back into application data.
    8. Data is validated.
    9. Data is restored into the appropriate storage mechanism.
    10. Application confirms restoration.

Output:
    A complete backup/restore workflow.

    A defined serialization architecture.

We combine all layers into one system.

    The official system architecture diagram.

################################################################################
# FINAL PROJECT PRINCIPLE
################################################################################

The project should be developed from requirements -> design -> implementation
-> integration -> testing -> polishing -> documentation -> demonstration ->
release.

We should not randomly jump between frontend, database, OOP, Git, and
statement parsing.

At any point in the project, we should be able to answer:

    - What phase are we currently in?
    - What individual step are we completing?
    - Why are we doing it?
    - What smaller tasks are required?
    - What should be produced when it is complete?
    - How will we test it?
    - When will we commit it?

That is the purpose of this master workflow.

The workflow therefore represents the complete lifecycle of the Personal
Finance & Budgeting Dashboard, from the original problem statement through the
final stable GitHub release.
